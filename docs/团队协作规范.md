# 团队协作规范

本规范与《版本与协作说明》配套执行，覆盖分支、提交频率、代码审查与合并发布。

## 1. 角色与职责

| 角色 | 职责 | 本项目演练账号 |
| --- | --- | --- |
| 开发者 | 在 feature 分支实现模块、自测、提交 PR | CYJcyj2005 |
| 审查者 | 按清单审查 PR，给出意见并 Approve | cyj099 |
| 集成者 | 合并 PR、处理冲突、执行 dev → main 发布 | cyj099 |

> 说明：本项目为个人课程设计，上述角色由本人的两个 GitHub 账号分别扮演，用于完整演练协作流程，不代表存在真实的第三方成员。

## 2. 分支策略与提交频率

- `main` 只接收来自 `dev` 的发布合并，始终保持可运行；
- `dev` 为集成分支，每周至少集成一次；
- `feature/<模块名>` 从 `dev` 拉出，生命周期不超过一周，合并后删除；
- 每完成一个可运行的小步就提交一次，至少每个工作日提交一次，避免一次性堆积大量改动；
- 提交前必须通过测试：`python -m unittest discover -s test`；
- 不提交数据库文件、密钥、调试输出与临时脚本。

## 3. 提交信息规范

采用 Conventional Commits，一条提交只做一件事：

| 前缀 | 用途 |
| --- | --- |
| `feat:` | 新增功能 |
| `fix:` | 修复缺陷 |
| `docs:` | 文档变更 |
| `test:` | 测试相关 |
| `refactor:` | 不改变行为的重构 |
| `merge:` | 合并提交 |

提交正文写清"做了什么、为什么"，涉及 Issue 时标注编号，如 `Closes #7`。

## 4. 代码审查要求

- 所有进入 `dev` 的改动必须经 Pull Request，禁止直接推送；
- 至少 1 名审查者 Approve 后才能合并；
- 审查清单：
  1. 改动与 Issue/需求描述一致，边界条件有测试覆盖；
  2. 不引入敏感信息（密码、Token、数据库文件）；
  3. 命名、注释与格式符合 PEP 8；
  4. 不破坏既有接口，相关测试全部通过；
- 审查意见在 24 小时内回复；作者修改后由审查者重新确认再合并。

## 5. 合并与发布

- `feature/* → dev`：使用 merge commit，保留完整分支历史；
- `dev → main`：每周一次，由集成者发起 PR，审查者 Approve 后合并；
- 合并冲突必须在本地解决、跑通测试后再推送；
- 发布合并后在 `main` 上打标签并同步更新文档。

## 6. Issue 流程

缺陷统一用 Issue 记录，包含复现步骤、预期结果与实际结果；PR 描述中用 `Closes #编号` 关联，合并后自动关闭。
